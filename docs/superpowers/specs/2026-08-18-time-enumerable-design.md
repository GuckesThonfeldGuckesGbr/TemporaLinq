# ITimeEnumerable & Date×Time Combinator — Design

**Status:** Approved for implementation planning
**Date:** 2026-08-18

## Problem

`TemporaLinq` today only models `DateOnly` sequences (`IDateEnumerable`, generated by `Dates`).
There's no way to express intraday time-of-day filtering (e.g. "every hour between 8 and 12") or
combine it with a date sequence to get concrete points in time (e.g. "every hour between 8 and 16
on weekdays"). Holidays-style work is considered filler; this is a core-library feature.

## Goals

- A `Times`/`ITimeEnumerable` type that generates ascending `TimeOnly` sequences, mirroring how
  `Dates`/`IDateEnumerable` generates ascending `DateOnly` sequences.
- A combinator that cross-joins a date sequence with a time sequence into an ordered `DateTime`
  sequence.
- Per-date-variant schedules (e.g. shorter hours on Fridays) are achieved by composing multiple
  cross-joins with the existing `Merge` operator — **not** by adding variation logic to any single
  type.
- A namespace reorganization that separates the domain-agnostic monotonic-sequence core (already
  shared with `TemporaLinq.Holidays`) from date-specific and time-specific code, since the new
  `Times` code needs a home and the existing flat structure doesn't have one.

## Non-goals

- No new `IDateTimeEnumerable` marker interface — see [Result type](#result-type) below.
- No per-day-of-week variation built into `Times` or the combinator.
- No midnight-wrapping time ranges (e.g. 22:00–02:00) — express as two merged ranges if ever
  needed.
- No convenience shorthands (`EveryHour()`, `EveryMinute()`, etc.) — `Every(TimeSpan)` is the one
  generation primitive.
- No bounding/validation against unboundedly large or infinite sequences — laziness is a deliberate
  property of this library, not a risk to guard against.

## Design

### `Times` / `ITimeEnumerable` (namespace `TemporaLinq.Times`)

```csharp
namespace TemporaLinq.Times;

public interface ITimeEnumerable : IMonotonicallyAscendingEnumerable<TimeOnly> { }

public record Times : ITimeEnumerable
{
    public TimeOnly StartTime { get; private init; }
    public TimeOnly EndTime { get; private init; }
    public TimeSpan Step { get; private init; }

    public static Times From(TimeOnly start) => new() { StartTime = start };

    /// <summary>
    /// The end time is exclusive, mirroring Dates.To.
    /// </summary>
    public Times To(TimeOnly end) => this with { EndTime = end };

    public Times Every(TimeSpan step)
        => step > TimeSpan.Zero
            ? this with { Step = step }
            : throw new ArgumentOutOfRangeException(nameof(step), "Step must be positive.");

    public IEnumerator<TimeOnly> GetEnumerator()
    {
        for (var time = StartTime; time < EndTime; time = time.Add(Step))
            yield return time;
    }

    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
}
```

Notes:
- No `Config`/calendar-equivalent property — a time-of-day range has no analogue to
  `CalendarConfig`'s weekend/calendar concerns, so nothing is carried.
- `StartTime >= EndTime` is not validated; it simply produces an empty sequence (same convention
  as `Dates`, which doesn't validate `StartDate`/`EndDate` ordering either).
- `Every` validates eagerly (fails fast at call time) since a non-positive step would otherwise
  loop forever silently on enumeration — the one place this design does add a guard, precisely
  because the failure mode (infinite loop) is categorically worse than the rest of the library's
  "just yields empty" convention.
- No LINQ-style operator surface (`Where`/`Select`/etc.) for `ITimeEnumerable` is added in this
  pass — not needed for the motivating use case, and can be added later the same way `DateLinq.cs`
  did for dates, if a concrete need arises.

### Combinator: `On` (namespace `TemporaLinq`)

```csharp
namespace TemporaLinq;

public static class DateTimeCombinators
{
    public static IMonotonicallyAscendingEnumerable<DateTime> On(
        this Dates.IDateEnumerable dates, Times.ITimeEnumerable times)
        => OnImpl(dates, times).AsMonotonicallyAscendingEnumerable();

    private static IEnumerable<DateTime> OnImpl(Dates.IDateEnumerable dates, Times.ITimeEnumerable times)
    {
        foreach (var date in dates)
            foreach (var time in times)
                yield return date.ToDateTime(time);
    }
}
```

(Namespace note: the snippet above qualifies `Dates.IDateEnumerable`/`Times.ITimeEnumerable` for
clarity in this doc; the actual file will use `using TemporaLinq.Dates;` / `using TemporaLinq.Times;`
and plain type names.)

`dates` × `times` is a full cross join (cartesian product), not a positional zip — every date gets
every time. Naming it `On` reads as "these dates, on these times" and avoids colliding with LINQ's
`Zip`, which means something different (positional pairing).

#### Ordering proof

Both inputs are already guaranteed ascending (`IDateEnumerable` and `ITimeEnumerable` both extend
`IMonotonicallyAscendingEnumerable<T>`). For any two consecutive dates `d1 < d2` in `dates`, every
`(d1, t)` pair is strictly less than every `(d2, t')` pair, because `TimeOnly` has no representation
for "past midnight" — the latest possible time on `d1` is still before `00:00` on `d2`. Combined
with `times` itself being ascending, date-major nested iteration (as written above) produces a
strictly ascending `DateTime` stream with no sorting or buffering required.

#### Result type

No new `IDateTimeEnumerable` interface is introduced. `IMonotonicallyAscendingEnumerable<DateTime>`
already expresses exactly the guarantee asked for ("ordered early to late"), and it already
composes with the existing generic `Operations.Merge<T>` (proven by `TemporaLinq.Holidays` using
the same generic interface for `Holiday`). Introducing a same-shaped marker interface would
duplicate something that already exists, which conflicts with the project's lean-by-default
direction. If DateTime-specific LINQ operators become worth having later (a `Where`/`Select`
surface analogous to `DateLinq.cs`), that's the point at which a dedicated interface would earn its
keep — not before.

### Composing per-day variation (the motivating example)

```csharp
using TemporaLinq.Dates;
using TemporaLinq.Times;

var monToThu = Dates.From(start).To(end)
    .Only(DayOfWeek.Monday, DayOfWeek.Tuesday, DayOfWeek.Wednesday, DayOfWeek.Thursday)
    .On(Times.From(new TimeOnly(8, 0)).To(new TimeOnly(16, 0)).Every(TimeSpan.FromHours(1)));

var friday = Dates.From(start).To(end)
    .Only(DayOfWeek.Friday)
    .On(Times.From(new TimeOnly(8, 0)).To(new TimeOnly(15, 0)).Every(TimeSpan.FromHours(1)));

var schedule = monToThu.Merge(friday);
```

No new API is needed for this — it's entirely existing `DateLinq.Only`, the new `On`, and the
existing generic `Operations.Merge<T>`.

## Namespace reorganization

The current flat `TemporaLinq` namespace mixes generic monotonic-sequence machinery (already
reused by `TemporaLinq.Holidays` for `Holiday`) with date-specific types. Since `Times` needs a
home, and the existing structure doesn't cleanly have one, this pass also splits the core project
into three namespaces:

```
TemporaLinq/                                    namespace TemporaLinq
  IMonotonicallyAscendingEnumerable.cs
  MonotonicAscendingEnumerableWrapper.cs
  LinqExtensions.cs        (generic First/FirstOrDefault/AsMonotonicallyAscendingEnumerable)
  Operations.cs             (generic Merge<T> only)
  DateTimeCombinators.cs    (new: the `On` extension)

  Dates/                                         namespace TemporaLinq.Dates
    Dates.cs
    IDateEnumerable.cs
    CalendarConfig.cs
    Weekends.cs
    DateEnumerableWrapper.cs
    DateLinq.cs               (Only/Except/EveryNth/BusinessDays/AsDateEnumerable)
    DateOperations.cs         (Merge/Union/Intersect/Except/Distinct overloads for IDateEnumerable,
                                split out of today's Operations.cs)

  Times/                                         namespace TemporaLinq.Times
    Times.cs
    ITimeEnumerable.cs
```

This is a breaking change for any code using `using TemporaLinq;` to reach `Dates`, `Weekends`,
`CalendarConfig`, etc. — those move to `TemporaLinq.Dates`. Both `TemporaLinq.Test` and
`TemporaLinq.Holidays` reference these types today and will need their `using` directives updated
as part of this work. Accepted explicitly as a scoped, one-time reorganization since there is no
known external consumer yet.

## Testing

New tests in `TemporaLinq.Test/`, mirroring the existing test layout:

- `TimesTest.cs` — generation over `From`/`To`/`Every`; exclusive-`To` boundary behavior; empty
  result when `StartTime >= EndTime`; `Every` throws on non-positive step.
- `DateTimeCombinatorsTest.cs` — cross-join produces exactly `|dates| × |times|` results in
  ascending order; the Mon–Thu/Friday `Merge` example from this spec, verified end-to-end.

Existing tests (`DatesTest.cs`, `LinqExtensionsTest.cs`, `OperationsTest.cs`, `BusinessDaysTest.cs`,
`PredicatesTest.cs`, `CacheTest.cs`, and everything under `Holidays/`) need their `using` statements
updated for the namespace moves, but no behavioral changes are expected — this should be a
mechanical pass verified by `dotnet build && dotnet test` staying green.

## Open items for the implementation plan

- Exact ordering of the namespace-move commits vs. the new-feature commits (move-first is likely
  cleanest, so the new code lands directly in its final home).

`DateOperations.cs` is a mechanical split of today's `Operations.cs`: the `Merge<T>`/`Merge<T>(this
IMonotonicallyAscendingEnumerable<T>, ...)` generic overloads stay in `TemporaLinq/Operations.cs`
under `namespace TemporaLinq`; the `IDateEnumerable`-specific overloads (`Merge(this
IDateEnumerable, ...)`, `Except`, `Union`, `Intersect`, `Distinct`) move to
`TemporaLinq/Dates/DateOperations.cs` under `namespace TemporaLinq.Dates` with `using TemporaLinq;`
added for the generic `Merge<T>`/`AsMonotonicallyAscendingEnumerable<T>` they call into. No logic
changes either side of the split.
